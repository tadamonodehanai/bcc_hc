# ケアシル 構築手順（社内レビュー向け）

作成日: 2026-07-12 ／ 対象: ドメイン未割当の社内レビュー環境

## 0. 全体像（3分で把握）

```
ソースCSV (data/*.csv)            ← 人が編集する唯一の場所
   │  normalize（正規化＋スキーマ検証＋新着差分）
   ▼
公開データ (data/公開_制度.json)   ← 検証済みのみ。UIはこれの写像
   │  build（生成）
   ▼
kaigo-hojokin-portal.html  ポータル（逆引き・重層・提案書出力・新着）
hikaku.html                47県比較ビュー
review.html                レビュー画面（承認→公開ゲート）
teian.html                 施設向け提案書（印刷→PDF）

自動収集: crawler.py（日次）→ crawl_staging.json → 人がレビュー承認 → 公開反映
```

- **HTMLは4枚とも完全自己完結**（データ埋め込み・外部依存なし）。ファイルを開くだけで動く。
- 「未確認データは公開に出さない」「推測で埋めない」が全工程の設計原則。詳細は `data/README.md`。

## 1. 前提環境

| 必須 | 用途 |
|---|---|
| macOS / Linux + Python 3.9+ | パイプライン一式（標準ライブラリ中心） |
| pip: `pypdf` | 要綱PDFの本文抽出（`python3 -m pip install pypdf`） |
| （任意）Node.js | UI回帰テスト `scripts/test_portal.js`。無くても本体は動く |

```bash
# セットアップはこれだけ
cd <プロジェクトフォルダ>
python3 -m pip install pypdf
python3 scripts/pipeline.py refresh   # 全生成＋検証＋回帰テスト
python3 scripts/pipeline.py status    # 健全性ダッシュボード
```

## 2. LLM抽出の組み込み（APIキー設定と推奨構成）

抽出はLLM（高精度）とルールベース（フォールバック）の二段構え。**キー未設定でも全機能動作**しますが、LLMを有効にすると「申請締切と完了期限の区別」「表記ゆれ機器名の機器IDへの正規化」など抽出精度が上がり、確度昇格が自動化できます。

### 組み込み手順（4ステップ）

1. Anthropic Console（console.anthropic.com）で API キーを発行（組織のアカウント管理者に依頼。ワークスペースを分けて発行すると利用量を分離監視できる）
2. SDKを導入: `python3 -m pip install anthropic`（導入済みならスキップ）
3. **各自の環境変数に設定**（キーをチャット・リポジトリ・共有ドキュメントに貼らないこと）:
   ```bash
   echo 'export ANTHROPIC_API_KEY=＜発行したキー＞' >> ~/.zshenv
   source ~/.zshenv
   ```
4. 確認: `python3 scripts/pipeline.py status` の「LLM抽出」行が **有効** になればOK。コード変更は不要（クローラ・日次タスクとも自動で切替）。テスト実行: `python3 scripts/crawler.py --ids P-11 --extractor llm`

### 実装方式（実装済み・変更不要）

- **公式SDK（`anthropic`）＋ structured outputs**: 抽出スキーマ（締切/補助率/上限/機器タグ/抽出根拠）をAPIに渡し、**出力のスキーマ適合をAPI側で保証**。「JSONで返して」方式のパース失敗が構造的に発生しない。429/5xxのリトライはSDKが自動処理。
- **フォールバック連鎖**: LLM→ルールベース。キー未設定・SDK未導入・API障害のいずれでもクローラは止まらない。
- **レビューゲートは不変**: LLM抽出でも全レコードは「レビュー待ち」で人間承認を経てから公開。

### モデル選定（環境変数 `CARESIL_LLM_MODEL` で変更可）

| モデル | 料金(入力/出力 per 1Mトークン) | 使いどころ |
|---|---|---|
| `claude-haiku-4-5` | $1 / $5 | 最安。定型的な要綱の抽出には十分 |
| **`claude-sonnet-5`（既定）** | $3 / $15（2026-08-31まで導入価格 $2/$10） | **推奨**。締切/完了期限の区別など文脈判断と価格の均衡 |
| `claude-opus-4-8` | $5 / $25 | 難読・非定型の要綱、精度最優先の再抽出 |

### コスト目安と最適化

- 1制度ページ（本文16Kトークン上限＋出力4K）≒ Sonnet 5で**数円〜十数円**。日次は変更検知分のみ（通常0〜数件/日）なので**月額でも数百円規模**。
- **初回の全件一括再抽出（60件超）には Batch API**（`client.messages.batches.create`）を使うと**50%引き**。1時間以内に完了することが多く、日次のリアルタイム性は不要な用途に最適。
- prompt caching は本パイプラインでは効果が薄い（固定プロンプトが最小キャッシュ単位より小さく、本文が毎回異なる）ため未使用。将来プロンプトに機器マスタ全文等を含める場合は導入を検討。

## 3. 社内レビューでの共有方法（ドメイン不要）

### 案A: HTMLファイルをそのまま配る（最速・推奨）
4枚のHTMLは自己完結なので、**Slack/メール/共有フォルダでファイルを渡すだけ**。
受け取った人はダブルクリックで開ける。ネット接続も不要（出典リンクを踏む時だけ必要）。
- 渡すもの: `kaigo-hojokin-portal.html`（+必要に応じ `hikaku.html` / `teian.html`）
- 注意: ブラウザがキャッシュを持つことがあるため、更新版を渡したら**スーパーリロード**（Cmd+Shift+R）を案内。

### 案B: 社内LANで簡易ホスティング
レビュー期間中だけ、手元のマシンで:
```bash
cd <プロジェクトフォルダ> && python3 -m http.server 8080
# → 同一ネットワークから http://<このMacのIP>:8080/kaigo-hojokin-portal.html
```

### 案C: 一時URLでの限定公開
Netlify Drop / Vercel / Cloudflare Pages 等に4枚のHTMLをドラッグ&ドロップすると、**ドメイン割当なしで自動発行URL**（例: xxx.netlify.app）が得られる。社外サービスに置く判断になるため、掲載データが公開情報のみであることを確認の上、**Basic認証やアクセス制限を設定**して使うこと。

> 本番化（ドメイン割当後）は、案Cの構成をそのまま昇格するのが最短。生成物が静的HTMLなので、S3+CloudFront・Cloudflare Pages等どこでも動く。パイプラインはGitHub Actions等の日次ジョブに載せ替え可能。

## 4. 日次運用

- **このMacで運用する場合**: スケジュールタスク `caresil-daily-crawl`（毎朝6時）が登録済み。Claudeアプリのサイドバー「Scheduled」から確認・「Run now」で手動実行。初回に一度 Run now して権限を事前承認しておく。
- **アプリに依存せず cron で回す場合**:
  ```bash
  crontab -e
  # 毎朝6時: クロール→再生成（ログは logs/ に日付つきで保存）
  0 6 * * * cd <プロジェクトフォルダ> && mkdir -p logs && { python3 scripts/crawler.py --limit 15; python3 scripts/pipeline.py refresh; python3 scripts/pipeline.py status; } >> logs/daily_$(date +\%Y\%m\%d).log 2>&1
  ```

## 5. データ更新の運用ルール（レビュー担当者向け）

```
① crawler が変更検知 → data/crawl_staging.json（この時点では非公開）
② review.html を開く → 現公開値との差分・原文引用を見て 承認/保留/却下（＋必要なら締切等を編集）
③ 「決定をエクスポート」→ data/decisions.json に保存
④ python3 scripts/review.py apply --decisions data/decisions.json
⑤ python3 scripts/pipeline.py refresh  → 公開反映・新着に自動掲載
```

- 承認操作は全て `data/review_audit.jsonl` に記録される（誰が・いつ・何を）。
- **公開データ（公開_制度.json）は直接編集しない。** 手動修正はソースCSV → refresh。
- 新着・更新は公開時の差分から自動検知され、ポータル上部の「🆕 新着・更新情報」に14日分表示される。

## 6. セキュリティ・運用上の注意

- APIキーは各自の環境変数のみ。コミット・共有禁止。
- クローラはUA明示・robots尊重・1秒以上の間隔。自治体サイトに負荷をかけない。
- 掲載数値の最終責任は出典（公式ページ・要綱PDF）。UIの確度バッジ（確認済/概要確認）の意味をレビュー時に必ず説明すること。
- 年度替わり（4〜6月）は事業名・URLが一斉に変わる（実例: 滋賀県）。日次クロールの変更検知とリンク切れ検出が最も働く時期。

## 7. トラブルシューティング

| 症状 | 対処 |
|---|---|
| ポータルが古い表示のまま | ブラウザのスーパーリロード（Cmd+Shift+R） |
| PDF抽出が空になる | URLの日本語エンコード対応済み。それでも空なら真の画像PDF（現状は該当なし。OCRはSwift+Vision経路を用意済み） |
| スキーマ検証エラー | `pipeline refresh` の出力にID・理由が出る。該当CSV行を修正して再実行 |
| 回帰テスト失敗 | `node scripts/test_portal.js` で詳細確認。逆引き・重層の破壊を検知した状態なので公開前に必ず修正 |
