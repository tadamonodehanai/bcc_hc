## 逆引きの流れ（どう機能するか）

```
制度PDF/要項  ──クロール──▶  本文抽出（Claude）  ──▶  対象経費に含む機器を抽出
                                                       │
                          シノニム辞書で正規化 ◀───────┘
                                   │
                          機器ID（例: ROB-09 見守りセンサー）を制度に付与
                                   │
   利用者が「見守りセンサー」で検索 ──▶ ROB-09 を含む制度をすべてヒット
   （名称が「離床センサー」「眠りSCAN」でも同じ機器IDに寄るので取りこぼさない）
```

## 機器マスタの分類軸

- **大分類**: 介護ロボット / ICT / 介護福祉機器
- **厚労省重点分野**: 移乗介助・移動支援・排泄支援・見守り・入浴支援・介護業務支援（介護ロボットの告示分野に対応）
- **制度区分**: どの制度の対象経費になりやすいか（介護テクノロジー導入支援／デジタル化AI導入／人材確保等支援助成金 等）

制度側と機器側を機器IDで突合するので、UIの「対象機器から逆引き」チップがそのままこのIDに対応します。

## 制度リストの読み方（確度と一次情報）

`確度` 列で信頼度を明示しています。

- **高**: 令和8年度（2026）の現行情報を裏取り済み（S-001, S-002, S-004, S-005）
- **中**: 制度は実在・定番だが実額/締切は未確認（`要収集` の出典を埋める対象）
- **要確認**: 都道府県テンプレ行。実施有無・実額は各県要領で確定する前提

> 金額・締切・受付状況は毎年・自治体ごとに変わります。実運用では各制度カードの数値は必ず一次情報（出典URL/PDF）に直結させ、収集日時と変更検知を併記する設計です（プロトタイプのカード下部表示がその想定）。

## 東京「画像PDF」の真相解明とクローラ修正（2026-07-12）

OCR対応のつもりで着手したら、**誤診断だったことが判明**。東京のPDFは画像ではなく、クローラの `pdf_text` が**日本語ファイル名URLをエンコードせずダウンロード失敗**→空文字→「画像PDF」と誤記録していた。

- **修正**: `crawler.py` に `encode_url()`（パスの非ASCIIをquote）を追加し `pdf_text` に適用。回帰確認で同PDFから1,690文字抽出OK。自治体PDFは日本語ファイル名が頻出のため、この修正は全県のPDF取得成功率に効く。
- **東京を高へ昇格**: 概要・交付要綱PDFから直接抽出。導入支援=4/5、**導入推進事業=7/8（全国最高率・財団の条件付き）**、基準額 移乗/入浴125万・その他37.5万/台（推進133.4万）、**法人合計1,250万**。
- OCRは不要になったが、真の画像PDFが今後出た場合の手段は調査済み: tesseract/brew/pyobjcは本環境で不可、**Swift(6.3あり)+Vision framework が実行可能な経路**として温存。
- 教訓: 「抽出失敗＝画像PDF」と決めつけず、失敗原因を分類してログすべき（ダウンロード失敗/暗号化/画像/破損）。クローラの今後の改善点。
- **確度分布: 高20／中42**。

## 逆引きのバグ総点検（2026-07-12）

「逆引きはちゃんと機能しているか」の総点検。データ整合の機械チェック＋**本番HTMLの埋め込みJSを無改変でNode実行するテストスイート**（`scripts/test_portal.js`・DOMスタブ）で検証。

- **データ整合**: 全タグがマスタ存在／都道府県コードのJIS一致／市区町村コードの親県整合／埋め込み=公開JSON一致／死にチップなし → 全て✅
- **回帰テスト 10本**: 単一機器の包含/除外・FUK系・県×機器の重層・複数機器OR・実施主体フィルタ・検索併用・タグ空レコードの除外・締切カウントダウン・無条件全件 → **10 PASS / 0 FAIL**
- **発見したバグ1件（修正済）**: 沖縄の見守り(ROB-09)タグ欠落＝偽陰性。原因はシノニム辞書に「見守り機器」表記が無くクローラ抽出で拾えなかった。→ 辞書に「見守り機器/見守りテクノロジー/見守り」追加 → 沖縄を再クロール → **レビューゲート経由で承認**（正攻法・監査ログあり）→ ROB-09入りで公開反映。
- **調査上の注意（バグではない）**: ブラウザペインのfile://キャッシュが古いビルド（51件版）を表示し続けており、当初の「テスト失敗」はこれが原因だった。**ローカルでポータルを開き直す際はスーパーリロード推奨**。

- 例: 港区の施設で 国2＋都1＋港区1＝4件、上限合計目安 **1,000万円〜**（業務改善600万＋港区400万）。

## 運用仕上げ（2026-07-12）

- **ステージング自動クリア**: `review.py apply` が承認/却下の決着分を `crawl_staging.json` から除去、保留・検証NGは残置（実証: 5件→承認4除去→残1=保留のP-26）。
- **オーケストレータ `pipeline.py`**:
  - `refresh` … normalize→build_portal→build_review を一括再生成（標準運用: crawler→review apply→refresh）。
  - `status` … 公開件数・確度分布・レビュー待ち・上書き・監査行数・クロール最終確認・Tier1台帳、さらに**締切7日以内アラート**（受付中）。実行例で千葉/大阪=あと1日を検知。

## パイプライン全体像（上流→下流）

```
seed(47県CSV＋Tier1台帳＋国CSV)
  → crawler.py (取得・PDF・LLM/rule抽出・ハッシュ変更検知) → crawl_staging.json
  → review.html/ review.py (人手ゲート: 差分・根拠・承認/編集/却下＋監査) → reviewed_overrides.json
  → normalize_seido.py (範囲展開/曖昧日付null/数値正規化/override merge/スキーマ検証) → 公開_制度.json
  → build_portal.py → kaigo-hojokin-portal.html（逆引き・重層・提案書出力）
  → build_proposal.py → teian.html（施設向け提案書）
  pipeline.py が status/refresh で運用を束ねる
```
