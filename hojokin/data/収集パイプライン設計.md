# 収集パイプライン設計（信頼性・低バグ優先）

作成日: 2026-07-11 ／ ステータス: 設計たたき台

方針: **「壊れたデータ・不確実なデータをUIに絶対に出さない」** を最優先に据える。
情報の確実性は「①一次情報に直結」「②抽出結果を機械検証」「③確度が上がるまで公開しない」の3点で担保する。

## 0. 全体フロー

```
[1] シード         各自治体の起点URL（既収集の47県＋市区町村シード）
      │
[2] 取得          HTML取得 → 要綱PDFリンク検出 → PDFも取得（本文＋PDFの両方）
      │            ・robots/利用規約を尊重、1日1回・低速クロール
      │            ・取得日時と本文ハッシュ/PDFハッシュを記録
      │
[3] 変更検知       前回ハッシュと比較。差分なし→スキップ（コスト削減・誤更新防止）
      │            差分あり／新規→ 抽出へ
      │
[4] 抽出          LLM抽出（制度スキーマに強制。機器はシノニム辞書で機器IDへ正規化）
      │            ・フィールドごとに「抽出根拠（原文引用＋出典箇所）」を必ず返す
      │            ・自信度(0-1)をフィールド単位で付与
      │
[5] 検証(ゲート)   スキーマ検証＋整合性ルール（下記§3）。1つでも致命NG→ 公開停止
      │
[6] 確度判定       高／中／要確認 を自動判定（§4）
      │
[7] マージ         国→県→市の重層を突合、上乗せ/併用関係を付与、重複排除（§5）
      │
[8] 公開/保留      確度=高・中 → 公開DB。要確認・検証NG → レビューキュー（非公開）
      │
[9] 監査ログ       全レコードに 取得日時/出典/ハッシュ/抽出モデル/レビュー状態 を保持
```

要点: **公開DBと収集ステージングを分離**。UIは公開DBしか見ないので、抽出のブレやサイト改変が直接ユーザーに漏れない。

## 1. 一次情報への直結（確実性の根幹）

- すべての数値（上限・補助率・締切）は **公式ページ or 要綱PDF の該当箇所**に紐づける。
- レコードは `出典.公式URL` と `出典.要綱PDF_URL`、加えて **抽出根拠の原文引用** を保持。UIの「エビデンス」リンクはこれを指す。
- 集約メディア由来の値は **確度=中 止まり**。一次確認を通るまで `高` にしない（§4）。

## 2. 抽出（LLM）の作法

- 出力は `制度スキーマ.json` に**強制**（構造化出力）。自由文で返させない。
- **機器の正規化**: 原文の「離床センサー」「眠りSCAN」等は `シノニム辞書.csv` を介して `機器ID(ROB-09)` に変換してから格納。UIの逆引きはIDで一致するので表記ゆれに強い。
- **フィールド別の抽出根拠と自信度**を必須化。数値フィールドは「どのPDFの何ページ/どの表か」を残す。
- 不明な項目は**推測で埋めない**。`null` ＋ `要確認` とする（ハルシネーション防止＝バグ源を断つ）。

## 3. 検証ゲート（ここがバグを止める要）

スキーマ検証に加え、以下の整合性ルールを全レコードに適用。**致命NGは公開させない**。

| # | ルール | NG時 |
|---|---|---|
| V1 | `締切 >= 受付開始`（両方あれば） | 致命→保留 |
| V2 | `受付状況` と日付の整合（締切が過去なのに「受付中」等） | 自動補正＋警告 |
| V3 | `対象機器タグ` は機器マスタに存在するIDのみ | 致命→保留 |
| V4 | `カテゴリ`/`対象施設`/`受付状況`/`確度` は列挙値のみ | 致命→保留 |
| V5 | `確度=高` は 公式URL必須・数値フィールド非null・抽出根拠あり | 高→中へ降格 |
| V6 | 金額レンジ検査（例: 補助上限 1万〜5,000万を外れる） | 警告→レビュー |
| V7 | URL到達性（HTTP 200）・PDFリンク生存 | 404→リンク要修復フラグ |
| V8 | 重複検知（同一自治体×同一制度名×同一年度） | マージ or 保留 |
| V9 | 前回比の急変（上限が10倍等）| 警告→レビュー（改ざん/誤抽出の検知） |

補正は「安全側」に倒す。判断がつかないものは公開せずレビューへ回す（＝間違った情報を出すより、出さない）。

## 4. 確度モデル（確実性のライフサイクル）

```
要確認 ──(集約ページで発見)──▶ 中 ──(公式ページ/PDFで一次確認＋検証全通過)──▶ 高
   ▲                                                     │
   └──────────(検証NG・出典切れ・急変)──────────────────┘（降格）
```

- **高**: 公式一次情報で数値まで確認済み・検証全通過。UIで「確認済」バッジ表示。
- **中**: 制度の存在・URLは確か。数値は要綱PDF内など未確認。UIで「概要のみ確認」。
- **要確認**: 未確定/予告/抽出自信度低。**UIには原則出さない**（またはグレー表示で「詳細確認中」）。

現状の47県CSVは 福島・埼玉・沖縄・東京＝高、他は中。残りは日次クロールでPDFまで取得し順次「高」へ。

## 5. 重層マージ（国→県→市）

- 施設所在地の**市区町村コード**で「全国＋該当県＋該当市」を束ねる。
- `上乗せ元制度ID`/`併用可否` で親子・合算可否を判定し、詳細ページで **国＋県＋市の積み上げ**を提示。
- 同一制度が県ページと集約ページ両方で採れた場合は**一次情報を優先**してマージ（確度が高い方を採用）。

## 6. 日次クロールと運用

- 1日1回フルスキャン。**ハッシュ差分があるものだけ再抽出**（コストと誤更新の抑制）。
- 締切7日前以内は**高頻度チェック**（締切・受付状況のみ軽量再取得）。
- 予告（未定）は公開検知でフラグ→通知。
- 各更新は**差分ログ**を残し、UIの「最終更新／変更検知」表示に使う。

## 7. まず着手する順（低バグで確実に積む）

1. `制度スキーマ.json` を単一の真実として確定（本コミットで作成）
2. 検証ゲート（§3）をコード化 → 既存47県CSVを流して**現データの不整合を洗い出す**
3. 抽出プロンプト＋機器正規化を1県で確立 → 残り46県へ横展開（PDFまで取得し高へ昇格）
4. 公開DB／ステージング分離を用意 → ここで初めてUIを結線（UIは公開DBのみ参照）

この順なら、UI結線の時点でデータは検証済み・一次直結になっており、UI側の不具合は「表示だけ」の小さな範囲に閉じる。
